# Milestone 10, S3: registered project recipes

> **Lumi can now run ONE script that a project's own `package.json` declares, from a recipe you registered in Lumi's trusted UI, once per approval: `node.exe npm-cli.js run <script>` with the pinned Node.js under Program Files, a scrubbed environment, in its own Windows Job Object. It tells you when the run is ready, and Stop ends exactly that run's processes.**

> **It still cannot run a command you type, a model's command, an arbitrary executable or arguments, a shell or a terminal. It cannot install a dependency, run Git, edit `package.json` or a lockfile, or start a second copy of a running project.** Cross-app preparation is S4. Cross-executor recovery is S5.

## 1. Three authorities, three native confirmations

| Step | Where | Confirmation |
| --- | --- | --- |
| Register a project | runtime `projects` (migration `0019`) | Native folder dialog in main, then a native warning: **"This recipe executes code from this project with your user-level permissions."** |
| Register a recipe | runtime `project_recipes` | Trusted UI form, then a native confirmation showing the exact script text (and any `pre`/`post` hook) **read back from the runtime**, not from the renderer |
| Run once | `project_run` grant (R3) → `project_start` action | The renderer card, then a native confirmation of the **runtime's** card (argv shape, script, env names, readiness, timeout, warning) |

**Project roots.** A project root is separate from M10 file roots. It passes the same protection rules:

* no system, program or AppData folder;
* no profile, and no Lumi-owned tree (the runtime directory, browser profiles, the quarantine and the run scratch root);
* no reparse point.

It must contain a `package.json`. A project may not overlap a folder approved for saving downloads, and the reverse is refused as well. As a result, a download can never be placed where Lumi runs code.

## 2. The recipe

A recipe freezes all of the following into `spec`, and its SHA-256 `digest` is its identity:

* **Project identity:** the project's (volume, directory index).
* **Pinned executables:** `node.exe` and `npm-cli.js` under the Program Files known folder, each by path, (volume, index, size) and SHA-256. They are never looked up on PATH. A per-user Node.js is not used.
* **Script:** the script name, which must be declared by `package.json`, plus its text and its `pre`/`post` hook texts.
* **Package files:** the `package.json` and lockfile SHA-256, and the project `.npmrc` hash. A project with a `.npmrc` is refused, see §5.
* **Environment:** an allowlist of fixed name/value pairs. The following are refused:
  * secret-looking names (KEY, TOKEN, SECRET, PASS, AUTH, COOKIE, SESSION, PRIVATE, CERT, …);
  * `LUMI_*`, `DATABASE*`, `PG*`, cloud, Git, `NPM_CONFIG_*`, `YARN_*`, `PNPM_*`, provider and proxy prefixes;
  * `NODE_OPTIONS`, `NODE_PATH` and the other code-changing names;
  * every name Lumi sets itself;
  * secret-looking values;
  * control characters.
* **Readiness:** an HTTP port (1024–65535) and a plain path, or `exit_code`.
* **Timeout and stop policy:** a timeout of 5–600 s, and the one stop policy `terminate_job`. The database pins the stop policy with a CHECK.

At every run card and every start, `_current_recipe` re-derives all of this from the disk and the pinned Node.js. **Any difference invalidates the recipe permanently**, with a specific reason:

* `package_json_changed`, `lockfile_changed`, `script_changed`;
* `executable_changed`, `project_changed`;
* `project_npmrc_refused`;
* `digest_mismatch`, for a tampered stored spec.

Undoing the change does not revive the recipe: registering it again is a trusted act. A model can at most name a `recipe_id`.

## 3. A run

1. **Pre-checks (read-only), before anything is spent:**
   * the grant is ACTIVE and bound to this recipe revision and digest;
   * the recipe re-derives unchanged;
   * dependencies are present: `node_modules` if the project declares dependencies, and the `node_modules/.bin` entry of each script's first command. A missing one is **BLOCKED: `missing_dependency`**, with a `task.project_run_blocked` event. Nothing is installed, and the approval is not spent;
   * the readiness port is free (otherwise `port_in_use`).
2. **The run row is committed first** (status STARTING). The partial unique index `uq_project_runs_one_live_per_project` refuses a second live run (STARTING, RUNNING, READY or OUTCOME_UNKNOWN) of the same project. **Duplicate launch is decided by the database.**
3. **The attempt is committed**, through `start_scoped_attempt` with the step authorization consumed in SQL and the global-tier effect key `project_run:project:<id>`.
4. **The process is created SUSPENDED:**
   * **argv:** `[node.exe, npm-cli.js, "run", <script>]`, with `executable=` the pinned `node.exe` and `shell=False`;
   * **cwd:** the verified project root;
   * **environment:** built from nothing (see §4);
   * **job:** the process is assigned to a fresh kill-on-close Job Object whose only handle is the runtime's, and which has no breakaway permission;
   * **recorded:** its (pid, creation time) is **committed**;
   * **resumed:** only then does `NtResumeProcess` run. Until the resume, no project code has run.
5. **Supervision:**
   * The root's exit decides an `exit_code` recipe.
   * An HTTP recipe is READY only when **every** TCP listener on the port (IPv4 and IPv6, from `GetExtendedTcpTable`) belongs to a process that `IsProcessInJob` says is in **this run's job**, and a GET to `127.0.0.1:<port><path>` answers with a status below 400. A foreign listener, or a listener shared with a foreign one, is not the run.
   * If the run is not ready (or has not exited) within the timeout, it is ended.
6. **Stop** calls `TerminateJobObject` on that run's job only. It never kills by image name or bare PID. The test shows the server and its grandchild both end, and nothing else is touched.
7. **Log:** the last 200 lines, each at most 400 characters, with ANSI and control characters stripped. It is displayed as inert text labelled "Output from the project (not from Lumi)". It is never persisted, never sent to a model, and never part of an event.

A run cannot outlive the runtime: the job's only handle dies with it (kill-on-close). **Recovery** at startup (and the `reconcile` route) checks each live run row:

| Recorded | Evidence | Result |
| --- | --- | --- |
| no (pid, creation time) | the process was never resumed, so no project code ran | run FAILED `never_resumed`; start action reconciled FAILED |
| pid + creation time, process gone | `OpenProcess`, `GetProcessTimes` and `GetExitCodeProcess` show it is gone (a reused pid has a different creation time) | `ENDED_WITH_RUNTIME`; start action reconciled SUCCEEDED (it may have run, and it is over) |
| pid + creation time, still alive | — | `OUTCOME_UNKNOWN`; the project stays locked and the global tier blocks keyed effects |

## 4. The environment

The child's whole environment is built from scratch:

* `SystemRoot` and `windir`;
* `ComSpec` = `System32\cmd.exe`, because npm runs a package script through the Windows command processor;
* `PATH` = the Node.js directory plus `System32` plus the Windows directory;
* `PATHEXT`;
* per-run scratch folders for `TEMP`, `TMP`, `USERPROFILE`, `HOME`, `APPDATA` and `LOCALAPPDATA` under `%LOCALAPPDATA%\Lumi\project-runs\<run>`;
* empty, separate npm user and global config files, and a private npm cache;
* `npm_config_offline=true`, with the update notifier, fund and audit off;
* `npm_config_script_shell` pinned to `cmd.exe`, since npm ranks environment config above project config;
* the recipe's own allowlisted pairs.

The test plants these fake secrets in the runtime's environment and proves the child sees none of them, while it does see the recipe's own `APP_MODE`:

* `OPENAI_API_KEY`, `GEMINI_API_KEY`, `LUMI_RUNTIME_TOKEN`, `DATABASE_URL`, `GITHUB_TOKEN`, `AWS_SECRET_ACCESS_KEY` and `NPM_TOKEN`;
* `NODE_OPTIONS=--require ./evil.js`.

**What "no shell" means here, honestly.** Lumi itself never starts a shell, `cmd`, PowerShell, a `.cmd` shim or a terminal, and a source scan pins the single `Popen` call site and its argv shape. npm, however, runs a package script's text through the Windows command processor: that is how `npm run` works. The text it runs is the recipe's hashed script text, shown in the native confirmation. Any change to it invalidates the recipe.

## 5. Found while building S3: a project `.npmrc`

npm reads a `.npmrc` in the project folder. A test showed that `node-options=--require ./evil.js` in a project `.npmrc` **reached node** even with `npm_config_node_options=""` in the environment, because npm treats an empty environment value as unset. Rather than trust an override, the feature was narrowed:

* **refused:** a project with a `.npmrc` gets no recipe (`project_npmrc_refused`);
* **invalidated:** a `.npmrc` appearing later invalidates an existing recipe;
* **pinned:** `script-shell` is also pinned through the environment.

## 6. Acceptance C: "Open VS Code and start Lumi"

Acceptance C is three separate effects, each with its own authority, and none funds another. The test is `test_acceptance_c_open_editor_and_start_project.py`.

1. **Open the editor: M9 S3 registered launch, unchanged.** On this machine VS Code is a per-user install (`%LOCALAPPDATA%\Programs\Microsoft VS Code\Code.exe`). The registry **refuses** it, because a user-writable directory means the executable could be swapped. The test pins that refusal. **The rule is not weakened.** The launch half is exercised on the registered-launch path, using the fake desktop worker and a stand-in registered application under Program Files, with its own exact approval.
2. **The approved project:** a synthetic "Lumi" project, registered with the warning.
3. **The exact recipe run:** `npm run dev`. It is not started by the launch approval (`grant_not_active`), it becomes READY only when its own job owns the port, and it never touches the desktop worker.

The ledger shows two tasks, the launch's exact approval and one `project_run` grant, and a `project_start` action separate from the launch.

## 7. Electron

* **Bridge:** 15 fixed channels. None takes a path, command, executable or argument, and none is reachable from voice.
* **Recipe form:** closed. `recipeInput` refuses any extra key (such as `command` or `executable`), non-declared script shapes, ports below 1024, `..` paths, out-of-range timeouts, and bad env names or values.
* **`project-wire.ts`:** refuses a card whose argv is not exactly `node.exe npm-cli.js run <the card's script>`, a card without the exact warning or with another stop policy, and labels that carry an absolute path.
* **Supervisor allowlist:** pins `/projects*`, `/project-recipes*` and `/project-runs*`.
* **`ProjectPanel`** (inside Documents) renders the card, the script and the log as inert text.
* **Generic routes:** the generic action routes refuse `project_*` proposals and `project_start` attempts (`use_project_route`).

The first review attempt stopped early on a usage limit, and a fresh reviewer re-ran the full brief. It checked npm 11.17.0 behaviour directly in scratch projects. The lead found and fixed the project `.npmrc` issue in §5 before the review. Every finding below was verified against the code.

| 1 | **High** | npm walks UP from the project. A parent `package.json` with `workspaces` makes the parent npm's project prefix, so its `.npmrc` applies (reproduced: `node-options` injected). | 3 | Medium | The recipe dialog showed text from one read of `package.json`; registration re-read it later. | The route carries the confirmed script, pre and post texts. The runtime refuses on a mismatch (`script_changed_during_review`). Regression test. |
| 4 | Medium | There is a window between the start's re-derivation and the spawn. | `package.json`, the lockfile, `.npmrc` and the ancestor context are re-read immediately before the process is created. | 9 | Low | `cmd.exe` looks in the current directory first (an unhashed `node.cmd` would shadow `node`), and an ancestor's `node_modules\.bin` goes on PATH. | `NoDefaultCurrentDirectoryInExePath=1`; ancestor `node_modules` is refused (finding 1). |

## 11. Residual risks

* **npm executes the script text through `cmd.exe`.** The text is the recipe's, hashed and shown. Lumi adds no shell of its own.
* **A run executes the project's own code with the user's rights.** The job limits lifetime and ownership, not what the code may do while it runs. That is what the warning says.
* **A same-user process can still rewrite `package.json` after the spawn.** npm reads it itself. Lumi re-reads it immediately before the spawn but holds no deny-write handle across npm's own read.
* **A run whose process Windows will not describe (access denied) stays OUTCOME_UNKNOWN** and keeps the global-tier lock until reconciled (fail-closed).
* **The dependency pre-check is heuristic** (the first command of each script, and `node_modules`). A missing transitive module shows up as a failed run, never as an install.
* **No production-signed installed validation exists** (the certificate is not configured).
